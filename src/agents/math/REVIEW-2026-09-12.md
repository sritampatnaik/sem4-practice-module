| P1 | `tools.ts:172–184` | `1000000000000*(x^2-2)=0` returns no solutions, whereas `x^2-2=0` correctly returns both roots. ## Findings requiring correction

### P1 — Incorrect PSLE paper specifications in the retrieval corpus

At `data/syllabus/math.md:38`, Standard Paper 1 Booklet A incorrectly labels eight two-mark questions as short-answer; all 18 questions in that booklet are multiple-choice. At lines 47–49, Foundation Paper 1 should contain 20 multiple-choice questions and eight short-answer questions, totalling 46 marks. Paper 2 totals 34 marks, not 50. Multiple-choice questions include both one- and two-mark items. The same mistakes occur in `references/official-assessment/EXTRACTED-NOTES.md`.

Check the tables on page 2 of the official [Standard specification](https://isomer-user-content.by.gov.sg/334/fe51f29b-04ae-4fcb-a907-8db04c028510/0008_y26_sy.pdf) and [Foundation specification](https://isomer-user-content.by.gov.sg/334/5c51824e-16d2-47cf-bf64-ea5774beca04/0038_y26_sy.pdf). Correct both the notes and runtime summaries, then independently review the remaining examination facts before treating them as evaluation truth.

### P1 — Equation solving discards denominator restrictions

At `tools.ts:97`, only `rationalize(...).coefficients` is retained. Running `solve` on `(x^2-1)/(x-1)=2` returns `ok: true` with root `1`, although the original expression is undefined there and the equation has no solution. Retain the original domain and validate candidate roots, or explicitly reject rational expressions in this polynomial-only tool.

### P1 — Numerical approximation is reported as exact

At `tools.ts:18–26`, a tolerance check after `fraction(value)` does not establish mathematical exactness. Both `0.3333333333334` and `sqrt(1+10^-13)/3` return `exact: "1/3"`, accompanied by advice to prefer that answer. Preserve exact arithmetic from supported input expressions, or label this output as a rational approximation. Update the prompt and design claims accordingly. The [mathjs documentation](https://mathjs.org/docs/reference/functions/fraction.html) explicitly describes conversion from one numerical argument as a rational approximation.

### P1 — Advertised linear solving fails

At `tools.ts:119–122`, the linear case passes an explicit undefined quadratic coefficient to `polynomialRoot`. `solve("2*x+3=7")` returns `ok: false` and an argument-type error instead of `x=2`. Dispatch using the actual coefficient count, and include linear, quadratic and cubic cases in the repeatable tool checks.

### P2 — Undefined numerical results are returned as successes

At `tools.ts:203–204` and `tools.ts:230–243`, non-finite values are not rejected. `evaluate("1/0")` and the derivative of `sqrt(x)` evaluated at zero return `ok: true`; their infinite values become `null` in JSON. Define a consistent result contract for undefined, non-finite and unsupported results, including the `reason` field promised by the build plan.

### P2 — A tutoring preference is asserted as a universal marking rule

At `prompts.ts:20`, the instruction says a bare final answer is worth less than the same answer with steps. That is too broad. The PSLE specifications award full credit for a correct answer to a one-part short-answer question, and the [H2 specification, page 4](https://isomer-user-content.by.gov.sg/334/f27e37f7-f0ec-4a35-b1e8-3a5e88ae2f81/9758_y26_sy.pdf) generally permits unsupported graphing-calculator answers unless a question states otherwise. Encourage working for learning and potential partial credit; make statements about required working conditional on the actual question and paper. Synchronise the Langflow copy when amending this.

### P2 — New evaluation cases do not yet establish the claims they describe

At `src/evals/catalog/math.ts:297–302`, derivative mode is required in prose but only the tool name is checked. The current runner stores tool names without mode, arguments or results. Likewise, the H2 weighting case checks only `60`, so wrong AO1/AO3 values can pass. The new exact-fraction and integration cases use literal strings that reject valid LaTeX such as `\\frac{1}{2}` and `\\frac{x^3}{3}` under the existing scorer. The integration contract also says the tool cannot verify the answer, although differentiation is a valid verification of an antiderivative.

Keep these as development scaffolds until reviewed. Add deterministic calculation/domain checks and human-reviewed factual answers; coordinate richer tool evidence and mathematics-aware scoring with the shared evaluation owner. A tool invocation is not evidence that the calculation succeeded.

## Scope and plan alignment

- Restore the agreed preparation sequence: map all intended courses, review official references, select a pilot, then establish evaluated behaviour. `BUILD-PLAN.md` deliberately adopts prototype-first delivery while `DESIGN.md` requires reference review before finalising topic rules and gold answers. Exploratory code can remain provisional without redefining completion of the preparation steps.
- Make general mathematics help explicit. The syllabus anchors schoolwork and examination claims; it should not become an automatic refusal boundary for explicitly requested enrichment. The old topology-refusal case and the design wording still need reconciliation with this user decision and shared tutoring policy.
- Separate H1/H2 and other courses in the actual scope map. The new H2 assessment section correctly excludes polar-form complex numbers, but the old combined JC topic section still includes them. MF27 spans several courses, so presence on that sheet does not establish H1 or H2 topic coverage. These conflicts make course/cohort selection and reviewed exclusions necessary before using retrieval as authority.
- Keep examination specifications distinct from marking rubrics. The reference collection has not established official question-level marking schemes; the plan should not imply that adding paper formats completes rubric preparation.
- Repair document drift: the manifest contains 33 references, not 36; the plan says no Phase 0 prompt change before describing one; the runner limitation is final-step tool-call capture, not the first call per step. Preserve the existing shared-runner dependency rather than creating a separate Math framework.
